Agent 底层机制：
七层，自下而上

03/  Experience Needs

四层需求，
由内向外逐层成立

用户感知不到 Agent 在运行，就谈不上看懂它；看不懂，就没法有效控制；控制不了，就不会放心托付。设计投入应该先保证内层，再往外扩。

aliveness → legibility → agency → trust
可感知 · Aliveness它还在运行吗？
  • 区分思考中、输出中、等工具三种状态
  • 长任务显示已用时和当前动作
  • 离开后，完成或卡住时能收到通知
可理解 · Legibility它在做什么，为什么？
  • 按阶段压缩叙事，默认只给一句话
  • 决策说明带证据，不展示思考过程
  • 每句叙事都能回到原始记录
可控制 · Agency我能叫停或纠正吗？
  • 明确告诉用户现在能不能插手
  • 高风险操作前停下来等确认
  • 打断、纠偏、回退的后果说清楚
可信任 · Trust结果我敢直接用吗？
  • 结论如实标注：假设、推断还是已验证
  • 「已验证」必须附验证结果
  • 产物写明依赖了哪些证据
04/  Four Moments

人机协作的
四个时刻

和 Agent 协作时，用户只在四个时刻出现：交代任务、观察进展、必要时干预、最后验收。观察和干预并行发生，可以在运行中反复切换。

delegate · monitor · steer · adopt
01

委托：把模糊需求变成可确认的目标

Agent 复述目标、约束和完成标准，把它自己推断的约束单独标出来。用户只确认有疑问的部分，不用重写需求。

02

观察：只在需要时才被打扰

默认停在「扫视」距离：一行状态加阶段叙事。想看细节再逐层展开，不必一开始就面对工具日志。

02

干预：控制入口和真实时机对齐

能批准的地方给批准，能打断的地方给打断。界面不承诺做不到的事，比如「暂停后原样继续」，或撤回已经推送出去的修改。

03

采纳：验收的是证据，不是语气

交付时先给结论状态和证据，再给报告。用户核对的是「验证过没有」，而不是「它说得够不够自信」。

09/  Trust Calibration

目标不是更多信任，
而是恰当的信任

过程藏起来，用户会把每个结论重查一遍；叙事太流畅、措辞太笃定，用户又会不经核对直接采纳。好的界面让用户的信任程度和证据强度保持一致。

trust ≈ evidence
校准区：信任 ≈ 证据强度

过度怀疑

过程不可见，不确定的地方没有标注，失败被静默吞掉。用户只能全部重做一遍，Agent 等于没用。

恰当信任

结论分状态展示，证据一键可查，失败和压缩都留下痕迹。用户只抽查最关键的一两条。

过度信任

叙事流畅、语气笃定、满屏绿勾。用户不再核对，直到某个未经验证的结论出了事故。

假设：还没有证据找到证据 → 推断：有证据支持对照实验通过 → 已验证：附验证结果 另有观测：工具直接返回的事实

控制点上，
人和 Agent 交换什么

11/  Operator Development · Evidence Stages

算子开发里，
证据分四个阶段

算子从写完源码到真正上板，能拿到的证据逐级变强。每个调查视图都要先说清自己站在哪个阶段、能回答什么、还不能回答什么。用编译前的估算去回答上板的问题，是这个领域最常见的误导。

estimate ≠ measurement
01估算

编译前分析

依据：源码、计算图、性能模型、CPU Golden 参考

能回答：分块为什么变、搬运多少、理论瓶颈在哪

还不能：设备实际怎么执行

推导Pre-compile
02编译产物

编译后布局

依据：编译器分配报告、生成指令、源码映射

能回答：地址怎么分配、哪条指令对应哪行源码、Pass 改了什么

还不能：运行时的耗时和等待

编译Post-compile
03实测

上板执行

依据：设备执行与访存 trace

能回答：真实执行顺序、核间等待、实际带宽

还不能：数值是否正确

执行On-device
04已验证

数值校验

依据：匹配输入的真实 NPU 输出 + 测试规范

能回答：精度是否达标，优化有没有带来回退

还需要：跨设备、跨轮次的稳定性

验收Verified
证据弱证据强

例：RMSNorm 在 Ascend 950 上为什么改成两遍分块（第 01 阶段）

FP32 [2048, 16384]→ 整行 live 320 KiB超过UB 可用 248 KiB→ 两遍分块额外重读 X 128 MiB→ 理论时延 179.024 µs · mte2_bound

字节数和容量条件可以直接从源码推导、独立核对；时延和瓶颈分类来自 CANNBot 性能模型和仓库里保存的硬件标定数据。界面上这两类数字要分开标注，并写明「当前没有本机 NPU 实测」。来源分三种：实测、公开表、推导默认值，Mock 数据单独标出。

关注点

时间去了哪 →
领域映射算子的语义对不对？
  • 区分数学上的输入集合和源码实际请求的集合
  • 推导地址、分块和搬运布局
  • 保留分析前提，不把推导当运行结果
计算图元图形能不能一眼读懂？
  • Tensor、OP、数据角色用统一的正式图元
  • 保留标签结构和类别图标
  • 跨 Pattern 复用，不各画各的
证据工作台结论能不能被核对？
  • 对象选择、差异、源码依据放在一起
  • 当前选择可以复制或导出给 Agent
  • 标明实测、估算和 Mock
空间界面复杂关系能不能看全？
  • 无限画布、关联路径、浮动面板
  • 切换对象时保持视角
  • 平移缩放不改变当前选择

这四层能力是 Pattern 库里每个案例的共同组装方式：调查工作流按任务依次调用它们，用户不需要记住具体用哪个 Skill。对设计系统来说，这意味着沉淀的单位不只是组件，还包括「领域语义 + 图元 + 证据组织 + 空间交互」这一整套组合。
