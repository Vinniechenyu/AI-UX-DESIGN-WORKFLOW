Agent 运行架构：从模型推理到应用协作

模型生成下一步，运行时执行并管理状态，应用将任务、证据与产物连接为可协作的过程。

核心职责

负责目标接收、任务分配、人工确认与结果交付；复杂任务可采用单 Agent、多 Agent 或固定工作流。

运行方式

通过应用服务衔接任务入口、运行时和产物；需要协作时，明确各参与者的职责、交接条件与汇总方式。

依赖与边界

协作模式取决于任务结构；增加 Agent 不必然提高效果，权限、资源预算与完成标准仍需显式配置。

Agent 亲和条件
  • 目标可验收：把任务目标、约束、交付物和完成标准写清楚；区分“已执行”与“达到目标”。
  • 操作可调用：关键能力提供结构化工具或 API，说明前置条件、权限与返回结果，减少仅靠视觉猜测完成的操作。
  • 协作可交接：分工时传递任务范围、已有证据、未决问题和输出约定；汇总方负责解决冲突，避免子任务各自宣布完成。
  • 执行有边界：显式设置时间、调用次数、成本和权限；需要人工决定时给出问题、选项及影响，等待授权后再继续。
  • 交付可复用：产物附来源、版本、依赖与验证记录；保留继续执行的入口和任务状态，让后续 Agent 能接续处理。
核心职责

定义对象的身份、属性、状态和关系，使不同工具与服务能够引用和更新同一份业务对象。

运行方式

通过稳定 ID、数据契约和关联关系，连接任务、调用记录与产出；写入时检查结构、版本和引用是否有效。

依赖与边界

对象结构由应用定义，并非模型天然具备；结构校验通过，不代表对象内容或结论已经被验证。

Agent 亲和条件
  • 对象可寻址：为任务、文件、资源、证据和产物分配稳定 ID；不要只用“那个文件”或可变化的显示名称引用对象。
  • 字段有语义：名称、类型、单位、枚举和空值含义明确；时间附时区，数值附单位，区分未知、不适用与零。
  • 关系可追溯：显式记录属于、依赖、支持、反对、派生和取代关系；引用能解析到原始对象与版本。
  • 修改受约束：定义对象允许的状态转换和写入权限；并发更新检查版本或冲突，避免旧结果覆盖新状态。
  • 契约可演进：提供 schema 版本与兼容策略；保留旧记录的解读方式，结构校验和事实验证分别记录。
核心职责

在原始日志之外记录“发生了什么”：阶段变化、任务结果、发现与产物，并保存其来源和关联记录。

运行方式

运行时可以生成开始、结束和失败事件；模型也可通过结构化工具提交计划、摘要或判断，两类事件需区分来源。

依赖与边界

模型自报不等于执行事实；“完成”需要对应执行结果，“已验证”需要对应检查记录，不能仅凭叙述升级状态。

Agent 亲和条件
  • 事件有来源：区分运行时直接观测、模型自报和人工确认，附时间、任务 ID、调用 ID 与产生者。
  • 状态有依据：计划、进行中、成功、失败、待确认分别建模；成功引用执行结果，已验证引用具体检查记录。
  • 字段轻量明确：事件 schema 保持精简，只要求判断进展所需的字段；提供清晰描述与示例，降低反复上报的成本。
  • 记录可以对账：保留原始工具结果和异常；语义摘要能回到原始记录，不允许摘要替代失败事实或掩盖证据缺口。
  • 更新可辨识：每条事件有稳定 ID，重试可去重；修订通过版本或取代关系表达，避免互相矛盾的旧结论继续流通。
核心职责

管理指令、工具定义、对话、检索结果和任务记忆，为当前推理选择相关且可信的信息。

运行方式

通过检索、摘要、压缩或外部存储控制上下文规模；需要时将历史信息重新载入，子任务可使用独立上下文。

依赖与边界

上下文窗口不等于系统全部状态；外部文件、数据库与运行时可另存状态，压缩与检索也可能遗漏关键细节。

Agent 亲和条件
  • 状态可持久化：目标、约束、已作决定和待办写入结构化状态；关键内容不能只存在于即将被压缩的对话里。
  • 信息按需载入：上下文保留摘要与引用，原文可通过工具获取；检索结果带来源、时间与相关范围。
  • 来源有信任边界：区分系统指令、用户要求与外部资料；工具返回和检索文本应作为数据处理，不自动获得指令权限。
  • 压缩保留关键约束：摘要保留决定、未完成事项与证据指针，并标明删减；压缩后检查目标、权限和关键事实是否仍可恢复。
  • 交接有固定格式：子任务交回结论、状态、证据 ID 与未决问题；控制重复内容、过期记忆和上下文预算。
核心职责

连接模型与执行环境，管理工具调用、权限检查、超时、重试、中断和资源预算。

运行方式

模型提出工具调用后，由执行环境检查并运行；结果回到下一轮上下文，驱动后续动作或最终响应。

依赖与边界

模型提出动作不代表动作已经发生；暂停或取消不会自动撤销外部副作用，重试需要考虑幂等性与重复执行。

Agent 亲和条件
  • 工具声明副作用：说明只读或写入、影响对象、是否可撤回、预计耗时和成本；让运行时能按风险决定是否审批。
  • 重试遵守幂等：重复执行不会重复创建或重复扣减，或使用幂等键去重；先区分临时失败、输入错误和不可重试错误。
  • 执行有停止条件：设置步数、时间与费用上限；任务完成、等待人工、持续失败或预算耗尽时明确停止并记录原因。
  • 长任务可管理：返回任务句柄，支持查询进度、超时和取消；说明取消是否生效，以及已发生的副作用。
  • 恢复有检查点：保存已执行动作、结果和待执行步骤；涉及外部变更时定义补偿方式，不能把“重放”直接等同于“回滚”。
核心职责

区分消息角色、内容类型和调用身份，用工具名称、参数结构与结果字段表达一次完整的请求和响应。

运行方式

模型输出工具调用，执行环境返回对应结果；调用 ID 关联请求与响应，结束标记帮助运行时判断是否继续。

依赖与边界

字段名称和流式事件因接口而异；格式正确不等于参数有效或执行成功，返回结果仍需校验并保留错误信息。

Agent 亲和条件
  • 工具契约清晰：名称与描述写明用途、适用条件和副作用；参数注明类型、必填项、枚举和有效范围。
  • 请求结果可关联：调用 ID 与结果一一对应，保留成功、失败和取消状态；并行返回也不能丢失归属。
  • 结果大小有边界：返回摘要、分页或可获取全文的引用；截断必须显式标记，不能让模型把不完整数据当作全量。
  • 错误可以行动：返回错误类别、失败位置、是否可重试与修正建议；避免只有退出码或无上下文的“失败”。
  • 流式协议可恢复：区分参数片段、完整调用、内容结束与响应结束；参数完整并通过校验后再执行，断连时明确恢复策略。
核心职责

理解目标、分析已有信息，并生成下一步响应、计划或工具调用；这些输出需交由外部系统解释和执行。

运行方式

自回归语言模型基于上下文逐步生成 token；推理服务可将生成内容按流式片段返回。

依赖与边界

模型输出不是事实保证，也不会天然保存应用的长期状态；跨轮记忆、真实工具执行与结果校验依赖外围系统。

Agent 亲和条件
  • 输入清晰无歧义：目标、约束、术语与输出要求分开表达；提供必要背景，避免让模型猜测对象、单位或范围。
  • 内容便于处理：文本优先结构化，表格保留表头，数值附单位；图像任务提供必要原图与说明，避免丢失视觉证据。
  • 事实与假设分开：已知事实附来源，缺失信息明确标记；允许模型报告不确定或请求补充，而非补造结论。
  • 输出可以校验：需要机器消费时约定 schema、枚举与示例，并由程序验证；关键事实另用工具、测试或人工核查。
  • 预算匹配任务：为上下文、生成长度、延迟和推理成本设置预算；支持流式接收与取消，稳定前缀可在服务支持时利用缓存。

模型输出 · 调用提案

“想做什么”成为结构

type: tool_use
id: call_17
name: read_file
input: {path: "notes.md"}

模型选择工具并生成参数；实际执行由工具所在的环境负责。

流式参数可能分片到达。完整解析、校验通过后，才可进入执行。

运行时 · 执行边界

“能不能做”由规则判断

  • 参数有效：类型、必填项、路径或对象是否有效。
  • 权限允许：作用范围、副作用与授权是否匹配。
  • 资源可用：并发数、超时、调用次数与预算是否允许。

互不依赖的调用可并发；依赖前一步结果的调用要按顺序执行。

工具返回 · 执行事实

“发生了什么”回到模型

type: tool_result
tool_use_id: call_17
is_error: false
content: "文件正文…"

调用 ID 对齐请求与结果；失败也返回可识别的错误信息。

结果进入后续请求，模型据此决定继续调用、修正参数或回答。

一次响应 ≠ 一次工具调用同一响应可包含多项调用；每项都要关联自己的返回结果。
结束本轮 ≠ 任务完成输出上限、拒绝或错误都需要单独处理，不能统一显示“完成”。
调用成功 ≠ 结论成立读取成功只证明拿到了内容；事实与最终产物仍需按完成标准核验。
示意字段采用 Claude Messages 格式；客户端工具由调用方执行，服务端工具由服务方执行。状态与校验要求为应用设计建议。机制依据：工具循环 · 请求与结果关联

L2 展开：等待、失败与恢复，都要有明确的状态

等待需要明确对象，重试需要判断条件，恢复需要保存状态；任务应按完成标准或停止条件结束。

已接收排队 / 准备等资源，准备输入
运行中推理 / 生成得到调用或回复
按需等待等权限 / 补充保存状态，等明确响应
执行中调用 / 收集结果成功或失败都记入轨迹
检查结果继续 / 结束还缺信息 → 返回下一轮
分支 A · 等待

等待有明确的对象

  • 等用户：提出一个可回答的问题，并保存待确认动作。
  • 等工具：记录任务句柄、当前进度与已用时间。
  • 等资源：说明排队原因，不把等待显示成模型思考。

继续前核对授权和输入是否仍有效。用户拒绝时应取消该动作或调整计划。

分支 B · 失败

先分类，再决定重试

  • 临时故障：在预算内重试，并保留次数与失败记录。
  • 参数错误：先修正参数；重复同一次调用通常无效。
  • 结果不确定：先查询实际状态，避免重复产生副作用。

有外部写入的操作，应使用幂等键、结果查询或补偿机制保证重试可控。

分支 C · 恢复与结束

从记录接续，按标准结束

  • 恢复：加载检查点，确认已完成动作与外部状态。
  • 停止：达到时间、费用或次数上限时，记录原因与未完成项。
  • 交付：完成标准通过后，关联产物、证据和待用户决定事项。

恢复过程可能重新执行节点；已发生的外部操作不能只靠恢复对话撤销。

暂停与取消分别表达暂停在可恢复点等待；取消请求停止后续执行。已经完成的动作仍保留。
回滚与补偿分别表达可恢复的状态按版本回退；外部副作用通过各系统支持的撤销或补偿处理。
把运行机制接到体验状态说明回答“卡在哪”，可用动作回答“能做什么”，证据回答“能否信任”。
通用运行时设计示意，具体接口依框架而定；等待、重试和恢复须有实现支持。机制依据：Interrupts · Fault tolerance

08/  Trust Calibrationtrust ≈ evidence

目标不是更多信任，而是恰当的信任

信任应与证据强度保持一致；界面需要同时呈现结论依据、不确定性和验证范围，帮助用户判断是否采纳。

校准区：信任 ≈ 证据强度

过度怀疑

过程不可见，不确定的地方没有标注，失败被静默吞掉。用户只能全部重做一遍，Agent 等于没用。

恰当信任

结论分状态展示，证据一键可查，失败和压缩都留下痕迹。用户只抽查最关键的一两条。

过度信任

叙事流畅、语气笃定、满屏绿勾。用户不再核对，直到某个未经验证的结论出了事故。

假设：还没有证据找到证据 → 推断：有证据支持对照实验通过 → 已验证：附结果与适用范围 另有观测：工具直接返回的事实
